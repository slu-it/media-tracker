# 0003: pnpm, driven by Gradle

Status: accepted, 2026-09

## Context

The frontend is a Vite 8 + React 19 + TypeScript 6 app. Developers should not need a hand-installed Node
toolchain to produce a release, but frontend work should still have a fast native loop.

## Decision

- Package manager: pnpm 10.x, pinned in `frontend/package.json` (`packageManager`) and in
  `frontend/build.gradle.kts` (`node { pnpmVersion }`).
- Node 24 LTS and pnpm are downloaded by the `com.github.node-gradle.node` plugin (7.1.0). Gradle tasks
  `pnpmInstall`, `pnpmBuild` and `pnpmTest` wrap the npm scripts; `./gradlew build` is the contract for
  CI and releases.
- `cd frontend && pnpm dev` remains the hot-reload loop; the Vite dev server proxies backend paths.

## Reasons

- pnpm's content-addressed store is fast and disk-friendly, and its strict dependency layout avoids
  phantom imports. pnpm 10 also blocks dependency install scripts by default, which is a good default for
  a small project with few maintainers.
- Pinning exact versions everywhere (no `^` ranges) keeps `pnpm-lock.yaml` and the Gradle inputs stable.
- Gradle-managed Node removes "works on my machine" differences and needs no extra setup on CI or the Pi.

## Consequences

- node-gradle 7.1.0 predates Gradle 9. It has been verified with Gradle 9.7.1 and the configuration cache
  (`version` and `pnpmVersion` must stay literal strings, see plugin issue #350). If a future Gradle breaks
  it, replace the two `PnpmTask`s with `Exec` tasks calling Corepack's `pnpm`.
- Node 26 becomes LTS in October 2026; bump `node.version` then. Nothing else in the stack cares.
- Vite 8 (Rolldown, Lightning CSS) ships native binaries without install scripts, so no `allowBuilds`
  entry is needed today. If a dependency with a build script is added, allow it explicitly in
  `pnpm-workspace.yaml`.
