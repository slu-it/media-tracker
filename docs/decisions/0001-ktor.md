# 0001: Ktor as the server framework

Status: accepted, 2026-09

## Context

The backend is a small personal service with a login gate, a JSON API and static file hosting. It runs on
a Raspberry Pi with a 192 MB heap, so startup time and memory footprint matter more than ecosystem breadth.

## Decision

Use Ktor 3.5 (CIO engine) with kotlinx.serialization, Exposed for SQL and HikariCP for pooling.

## Reasons

- Kotlin-native, coroutine-based, no reflection-heavy container. Startup is well under a second and the
  baseline heap is small enough for the Pi budget.
- Everything needed is a first-party plugin: Sessions, Authentication, ContentNegotiation, StatusPages,
  CallLogging, static resources, YAML config with environment substitution.
- `testApplication` runs the real module in-process against H2 (replaced by a Testcontainers MariaDB in decision record 0015), so route tests need no running server.
- The Ktor Gradle plugin supplies the fat JAR without extra build code.

## Consequences

- Blocking JDBC (Exposed 1.x) must be kept off the event loop; `db/DatabaseFactory.kt` provides `dbQuery`
  which wraps transactions in `Dispatchers.IO`.
- Ktor and Kotlin release in lock-step; keep Ktor at 3.5.1 or newer for Kotlin 2.4 compatibility.
